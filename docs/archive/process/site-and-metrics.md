# Knowledge Base Site & Delivery Metrics

Status: Design — for Product Owner review
Last updated: 2026-09-17

## Product Owner decision

> *"I don't want pages to always have to be generated on demand, there should be
> some deterministic routine to convert the markdown into a site. The site will
> also show metrics on squad health, delivery performance etc so this will grow
> into analytics. Happy to start with markdown readable and cross-referenced in
> GitHub if that's simpler start."*

This is correct and worth stating as a principle:

**Documentation generation must be deterministic, not agentic.**

An agent regenerating pages on demand gives you a site that differs subtly every
time, cannot be diffed, and quietly rewrites history. A build script gives you
the same input → same output, reviewable in a pull request, runnable in CI.

**Agents author markdown. A build script renders it. The two never mix.**

## Phasing

| Phase | Deliverable | Status |
|---|---|---|
| **1** | Cross-referenced markdown in the repo, readable on GitHub | **Now** |
| **2** | Static site generated by a build script, published by CI | Next |
| **3** | Metrics collection from GitHub and repo history | After |
| **4** | Analytics dashboard on the site | Later |

Phase 1 is genuinely useful on its own — GitHub renders markdown, resolves
relative links, and gives you history and review for free. Phases 2–4 add reach
and insight, not correctness.

## Phase 2 — the build

**Principles:**

- Markdown in `docs/` is the single source of truth.
- The build is a pure function: same input, same output, no network, no model.
- It runs locally and in CI identically.
- A broken cross-reference fails the build. Documentation rot becomes a build
  error rather than a slow decay.

**Recommended stack:** a static site generator over a bespoke script — it gives
navigation, search and cross-linking without maintenance. The build must run in
CI and publish to GitHub Pages, with the site never hand-edited.

**Build-time validations** (each failing the build):

- Every internal link resolves.
- Every spec referenced by an issue exists.
- Every ADR has the required sections and a status.
- No spec is left in `Draft` beyond a configurable age — catches specs that were
  written, never approved, and quietly implemented anyway.

That last one is the interesting check: it detects a process failure, not a
content failure.

## Phase 3 — metrics

### Principle

**Measure the process, not the people.** There are no people here to measure —
which makes this a rare chance to instrument delivery honestly, without the
distortion that arrives the moment a metric affects someone's standing.

The purpose is to answer: *is this operating model actually working, and where
does it break?*

### Sources

All derivable from GitHub and repo history — no manual entry, which keeps
collection deterministic:

| Source | Yields |
|---|---|
| GitHub issues | Cycle time, escalation rate, rework, scope changes |
| Git history | Change size, churn, spec-to-code lag |
| PR reviews | Defect counts, QA catch rate, review turnaround |
| CI runs | Test pass rate, build health, flakiness |
| `docs/` | Spec coverage, ADR count, doc freshness |

### Metrics worth collecting

**Delivery performance** — familiar DORA-adjacent measures, adapted:

| Metric | Definition | Why it matters here |
|---|---|---|
| Cycle time | Issue opened → merged | Baseline throughput |
| Spec-to-code lag | Spec approved → implementation started | Is the spec gate a bottleneck? |
| Rework rate | Issues reopened, or PRs with >2 QA rounds | Proxy for spec quality |
| Change failure rate | Merged changes needing a follow-up fix | Standard health measure |

**Squad health** — specific to this operating model, and the more interesting set:

| Metric | Definition | Signal |
|---|---|---|
| **Escalation rate** | Questions raised per issue | **Near zero is a red flag** — agents are guessing rather than asking |
| **QA catch rate** | Defects found by QA ÷ total defects | Low means QA is not adversarial enough, or shares too much context with the Engineer |
| **Spec churn** | Edits to a spec after approval | High means intent is not being captured first time |
| **Escalation resolution time** | Question raised → answered | **Measures you** — this is the human bottleneck |
| **Acceptance criteria coverage** | Criteria with a corresponding test | Verification completeness |
| **Rework attribution** | Rework traced to spec vs implementation | Tells you which layer to invest in |

### The metrics that will actually teach you something

Three deserve particular attention, because they are counter-intuitive:

**Escalation rate — where zero is bad.** Every other delivery metric you know
rewards fewer interruptions. This one inverts: an agent that never asks
questions is not being efficient, it is guessing. A healthy squad escalates
regularly. If escalations drop to near zero, check whether specs genuinely got
better or whether agents started filling gaps silently.

**Rework attribution.** Splitting rework into "spec was wrong" versus
"implementation was wrong" tells you where to spend effort. Spec-side rework
means invest in the BA and your own intent-setting. Implementation-side means
invest in acceptance criteria and QA. Most teams measure total rework and learn
nothing actionable from it.

**Escalation resolution time.** This measures *you*, and in a spare-time project
it will likely be the dominant constraint. Worth knowing honestly rather than
assuming the agents are the slow part.

### Anti-metrics — deliberately not collected

| Not measured | Why |
|---|---|
| Lines of code | Rewards verbosity; agents can generate any amount |
| Commits per agent | Meaningless when commit granularity is arbitrary |
| Velocity / story points | Estimation has no meaning when implementation is near-free |
| Time per agent | Wall-clock time is dominated by model latency, not quality |

Stating these explicitly matters: they are the metrics a dashboard will tempt
you to add because they are easy to collect.

## Phase 4 — the dashboard

Lives on the generated site. Reads a metrics JSON file produced by the
collection script, so the dashboard is a pure rendering of collected data —
same determinism rule as the docs.

Sections:

1. **Now** — open issues by state, pending escalations, specs awaiting approval
2. **Delivery** — cycle time and throughput trends
3. **Squad health** — escalation rate, QA catch rate, rework attribution
4. **Quality** — test coverage, criteria coverage, build health
5. **Documentation** — spec coverage, ADR count, stale docs

**The "Now" section matters most in practice.** Pending escalations and specs
awaiting approval are your queue. If the dashboard shows nothing else useful, it
should show what is waiting on you.

## Open questions for Product Owner

1. Public or private site? Private keeps squad data considerations simple;
   public makes it shareable as an example of the operating model.
2. Should the metrics collection run on a schedule, or only on merge?
3. Do you want the KB to cover the operating model generically, or stay
   coaching-app specific? Generic makes it reusable for your next project — and
   potentially for the day job.
